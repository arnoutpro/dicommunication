What this is (and is not)

Dicommunication is a trusted-network admin workstation. Use it on the PACS VLAN, a lab, or a jumphost that can reach DICOM and HL7 ports. Configure this machine as a DICOM Application Entity, register remote nodes, impersonate extra calling AE Titles when a modality identity is required, and run the checks a connectivity ticket actually needs.

It is not a PACS, not a viewer, and not a replacement for vendor modality simulators. It does not keep a clinical image archive. The Windows (MSI) and macOS (DMG) installers run it as a background service that you open in a browser, with sign-in always on. Docker Compose and a local Python process serve the same UI in a browser too. The page only exists after the backend is already running — you cannot install Python from inside this UI.

See About for the version of this process, the calling AE Title, the listen port, and the data directory on this computer.

Security, sign-in and roles

On one computer with no accounts the app opens without a login. As soon as it can be reached from another computer, sign-in is required and HTTPS is used (a certificate the app makes itself, so the browser warns once; Configuration > Security shows its fingerprint and offers it for download). Docker Compose publishes port 8080 on 127.0.0.1 only; DICOMM_HTTP_BIND=0.0.0.0 opens it to the network. Do not publish port 8080 to the internet.

Sign-in details. Passwords are at least 12 characters and stored only as hashes. Five wrong passwords lock that name or address for five minutes, and a session ends after 30 minutes without use. In the Windows and macOS service editions sign-in is always on, even when only this computer can reach the app.

Roles. A viewer sees the status dashboard, the C-ECHO board and the simplified page. An operator also runs the tools and Router rules, but only against saved nodes and the folders an administrator lists under Configuration > Security (the folder Browse dialog is for administrators). An administrator does everything, including Users, Security and the Audit log. The first administrator is created on the computer itself, or with --create-admin NAME --password-file FILE.

Audit and retention. The audit log records who did what, never patient data, and detects edited lines. The Router history keeps counts only, never patient names or IDs. Rows fetched by a tool are emptied after 30 minutes (adjustable; 0 keeps none), and runs and results are deleted after 30 days (adjustable). See SECURITY.md for the details and what this does not cover.

Do not point it at production archives unless you intend to send the test C-STORE instance (patient ARNPRO^TESTBENCH / ID ARNPRO-TEST) or real Encapsulated PDF documents you import.

DICOM and HL7 are sent in the clear unless you terminate TLS elsewhere. HL7 send transmits whatever you paste. PDF to DICOM reads files you upload, ZIP contents, and any workstation path you type — treat that like a diagnostic console, not a public website.

The user interface

The left sidebar is a tree, like a file explorer. At the top is the tool switcher that picks the product: Dicommunication, Dicomtag Analytics, Dicom Anonymizer, Dicom Router, Dicom Cleaner and Dicom Import. Below it is that product's own menu; the Dicommunication product has Dashboard, Testbench, C-ECHO board, Worklist and the Connectivity / DIMSE / HL7 tool groups. Groups fold: open the triangle to expand; the group containing the current page stays open, and your open/closed state is remembered in this browser. The selected row is a solid colour across the sidebar.

Configuration is at the bottom of the left sidebar (administrators only). It is not a product: it is shared by all of them, and while you are in it the menu lists Configured nodes, Local DICOM AE, Virtual AEs, Remote nodes, Import / export, Users, Security, Audit log and Logs. Under it the AE chip shows this workstation's calling AE Title, the listen port and how many virtual identities you have saved.

The top bar holds the arnout.pro A mark and product name on the left and, on the right, About (this installation's version, AE and data folder), Help (this page), your account and Sign out when sign-in is on, and the theme control (Light, Dark, Follows device setting, or Professional dark; new installs open in Light). The look is deliberately flat and dense: square corners, thin lines, small type. Forms put the label on the left and the box beside it, as wide as what goes in it; an explanation is a ? you can hover instead of a paragraph, and advanced options are folded away. The area where data is shown is one flat surface.

Most tool pages use HTMX: the form posts without a full page reload, and the result panel updates in place. Long DIMSE operations can take tens of seconds; wait for the result rather than clicking again.

DICOM services this tool distinguishes

A working C-ECHO (or Orthanc answering MWL in its own UI) does not mean Storage or Query/Retrieve will succeed. These are different SOP Classes. That difference is the point of the Testbench.

UI name DIMSE SOP Class What it actually tests
C-ECHO C-ECHO Verification 1.2.840.10008.1.1 Association plus a DICOM ping. Connectivity only.
C-STORE C-STORE Secondary Capture Image Storage Can the peer receive an instance? Orthanc usually yes; an MWL-only RIS usually no.
PDF to DICOM C-STORE Encapsulated PDF Storage 1.2.840.10008.5.1.4.1.1.104.1 Wrap a PDF as a DICOM document (modality DOC unless you choose another) and store it. A peer that takes Secondary Capture may still reject Encapsulated PDF.
C-FIND C-FIND Study Root Query/Retrieve FIND Search stored studies in a PACS archive at STUDY level. Zero matches can still be a successful Q/R C-FIND.
Dicomtag Analytics C-FIND Study Root Query/Retrieve FIND Reached at /tools/c-find-advanced in the sidebar (formerly C-FIND Advanced). Study, Series, or Image plus Vue ELSCINT1 keys. List SR series from Study results; optional C-MOVE of those reports onto this AE.
MWL C-FIND / Worklist C-FIND Modality Worklist 1.2.840.10008.5.1.4.31 Search scheduled procedures, not the archive.
Send Image to PACS C-FIND (Study or Patient Root, or none for manual entry), C-STORE Study Root Query/Retrieve FIND, Patient Root Query/Retrieve FIND, then Secondary Capture Image Storage Reached at /tools/send-image in the sidebar. Find a study — by Study Root C-FIND (open or already closed, since this is against the archive, not Modality Worklist), by Patient Root C-FIND (for an order with no image yet stored at all, but a registered patient), or typed in by hand — pick it, choose a modality and a few descriptive tags, and C-STORE a small solid-black placeholder image carrying that study's Patient/Study/Accession identifiers. No real pixel content.
Dicom Router C-FIND, optional C-MOVE + C-STORE Study Root Query/Retrieve FIND (MOVE/STORE for retrieve-and-forward) Reached at /router in the sidebar. Same FIND as Dicomtag Analytics, but scheduled/automatic instead of manual, with an optional automatic retrieve-and-forward to one or more destination nodes.
Dicom Anonymizer C-FIND, C-MOVE Study Root Query/Retrieve FIND and MOVE Reached at /tools/anonymize in the sidebar. A Study-level C-FIND, an optional Series-level C-FIND to list a study's series, then a C-MOVE of the chosen studies or series to this workstation's Storage SCP. The instances are anonymized in memory and written to a folder or ZIP; nothing is sent back.
Tag Editor C-FIND, C-MOVE, C-STORE Study Root Query/Retrieve FIND and MOVE, then storage back Reached at /tools/tag-editor in the sidebar. Corrects two private Vue report tags on a study and stores it back.
Dicom Cleaner C-FIND, C-MOVE, C-STORE Study Root Query/Retrieve FIND/MOVE, then Storage back out Reached at /tools/dicom-cleaner in the sidebar. Study-level C-FIND, C-MOVE retrieve, blacks out one operator-configured rectangle of pixel data on every retrieved instance, then C-STOREs the cleaned instances back to a PACS.
Dicom Import C-STORE Storage out, from files on disk Reached at /tools/dicom-import in the sidebar. Scans a folder for a DICOMDIR and/or DICOM files, summarises them, lets you change patient and exam details, then C-STOREs the images to a PACS. Nothing is stored.

MWL C-FIND and the Worklist page are the same SOP Class. Study Root C-FIND is not. Orthanc without the worklist plugin typically accepts Verification, Storage, and Q/R, then rejects MWL. The Testbench and Worklist results show accepted vs rejected presentation contexts so that is visible.

Calling AE vs Scheduled Station AE

Two AE Titles matter on a worklist query, and they are easy to mix up:

  • Calling AE Title — who you are on the association. The remote must allow this AE (Orthanc DicomModalities, vendor “known AEs”, and so on).
  • Scheduled Station AE Title — a query key in the MWL identifier. Modalities normally ask for procedures scheduled to their own station (CT1, MR1, …).

On Worklist, Testbench, Dicomtag Analytics, Dicom Anonymizer, Dicom Cleaner, Dicom Import, Send Image, Tag Editor and each DIMSE tool, Present as chooses who you are:

  • (workstation) — the Local DICOM AE Title from Configured nodes
  • a virtual identity — calling AE plus that identity’s station / modality defaults

The result header shows as CT1 (or whatever calling AE was used). Every virtual calling AE must be allowed on the remote, the same way the workstation AE is.

Dashboard

Open

The home page has a Status panel: this workstation's calling AE and where it listens, whether Accept C-STORE and the Worklist SCP are listening, how many remote nodes answered the last C-ECHO (with a button to C-ECHO all of them), and a suggested next step. Below it, the remote-node table is the same list as Configured nodes, with a last C-ECHO badge when the C-ECHO board has been run, and shortcuts to PING, C-ECHO and the Testbench for that peer.

Recent results is a short timeline of the last tool runs (capped in storage at 200). Start with Network PING, then C-ECHO, then the DIMSE service you actually care about. A green C-ECHO here does not mean Storage or MWL will work.

Configured nodes

Open

This is the station identity: this workstation, virtual calling AEs, and remote DICOM nodes. Settings are saved on disk in the data directory and kept when you rebuild Docker or upgrade the MSI / DMG (an installer upgrade keeps the service's data folder). The overview is one summary line and three tables. Add or edit on the child pages: Local DICOM AE, Virtual AEs, Remote nodes. On Local AE, Accept C-STORE (Structured Reports) is on the main form; Advanced settings hides PDU, timeouts, and the MWL SCP.

The same menu also has Import / export, Users (accounts and roles), Security (sign-in and HTTPS status, how long fetched rows and run history are kept, and the folders operators may read), Audit log (who did what, with a check that nobody edited it) and Logs.

Local DICOM AE

Open

This is the real Application Entity of this software: listen address, listen port, timeouts, and the default calling AE Title when you are not impersonating a modality. The listen port is one workstation AE. Virtual titles do not add extra SCP ports.

Virtual AEs

Open

A modality does not query worklist as a generic workstation. It associates as CT1 (calling AE) and asks for scheduled procedures for station CT1.

Virtual local AE titles are saved impersonation identities for outbound associations. Add as many as you need (CT1, MR1, US1, …). They do not listen. For Orthanc, add each one to DicomModalities.

Field Meaning
Display name e.g. CT scanner 1
Calling AE Title Who you are on C-ECHO, C-STORE, C-FIND, and MWL
Station AE Title Worklist query filter. Empty means “same as calling AE”.
Default modality Optional MWL / Q/R filter (CT, MR, …) filled when you pick this identity
Notes Room, vendor, Orthanc modality key — not sent on the wire

Logs

Open

The Logs page has two parts:

  • Amount and file size — log level (DEBUG, INFO, WARNING, ERROR), maximum size of the current file (1–50 MB), and how many rotated files to keep. Changes apply immediately to this process and are stored in config.json.
  • Log view — the tail of dicommunication.log, refreshed every two seconds. Download the current file, or clear it (rotated files stay).

INFO records startup, configuration changes, tool runs, and MWL SCP start/stop. That is the usual setting on a PACS workstation. DEBUG also records HTTP requests (except health, static files, and the live tail poll). The console window on Windows shows the same stream.

Testbench

Open

One form to send C-ECHO, C-STORE, Study Root C-FIND, or Modality Worklist C-FIND to a selected remote, optionally as a virtual AE. Use this when you need to prove which SOP Classes a peer actually offers, not just that the port answers.

  • C-STORE sends a 16×16 Secondary Capture: patient ARNPRO^TESTBENCH / ARNPRO-TEST, modality OT. Look that instance up on the PACS if Storage was accepted.
  • C-FIND is Study Root, STUDY level. Leave filters empty for a broad query. Optional: patient name/ID, accession, study date, modality (ModalitiesInStudy).
  • MWL C-FIND uses the worklist SOP Class and the identity’s station AE unless you override it.
  • The result lists SOP Classes negotiated (accepted vs rejected) plus returned/stored records and the association log.

The individual DIMSE tool pages under DIMSE in the sidebar use the same engines. Testbench is the place to switch services on one remote without leaving the page. Choose the DICOM service and only the fields that service uses appear: the C-FIND filters for C-FIND, the station AE and scheduled date for MWL C-FIND, nothing extra for C-ECHO and C-STORE. The explanation of each field is a ? you can hover.

C-ECHO board

Open

Runs Verification against every configured remote in one click (up to 8 in parallel). Uses the workstation calling AE, not a virtual identity. The Dashboard table picks up the last pass/fail badge from this board. Also available as POST /api/echo-board/run.

Use the board as a morning check that DICOM ports still answer. Then use Testbench (or the individual tools) for Storage, Query/Retrieve, or MWL on the node that matters.

Worklist

Open

/worklist is the table view for Modality Worklist C-FIND (1.2.840.10008.5.1.4.31). It is not Study Root C-FIND. Use the Testbench for C-STORE and Q/R C-FIND.

Query worklist

  • Source — local web worklist, or a remote node marked as providing Modality Worklist
  • Present as — workstation or a virtual AE
  • Filters — patient name (DOE* style), patient ID, accession, modality, station AE, scheduled date

Empty filters on a remote mean “return what the SCP is willing to send”. Presenting as CT1 fills station (and modality, if the identity has one) unless you override the fields. Zero rows with a Pass still means the SOP Class was accepted — check station AE, date, and Present as.

Local web worklist

Add scheduled procedures here. If Worklist over DICOM (serve the web worklist as an MWL SCP on the listen port) is on under Local DICOM AE, a modality can C-FIND this workstation on the listen port (11112 by default). The local MWL SCP also answers C-ECHO. It uses the workstation AE Title, not virtual identities.

Network PING

Open

DNS resolve, ICMP echo, then TCP connect to the DICOM port of the selected remote. That TCP step is the same kind of check as PowerShell Test-NetConnection -Port; a separate Test-NetConnection tool would overlap. ICMP is often blocked on clinical networks; the TCP check is the useful layer-4 result. A successful TCP connect does not prove DICOM — only that something is listening. Follow with C-ECHO.

C-ECHO

Open

Verification SOP Class 1.2.840.10008.1.1. Associates with the selected remote as the chosen calling AE and sends C-ECHO. A pass means the peer accepted Verification and answered. It does not mean the peer will accept Storage, Study Root FIND, or Modality Worklist.

If the association is rejected entirely, the calling AE is not in the peer’s allow-list, or host / port / called AE are wrong. Check Configured nodes and the vendor “known AEs” list (Orthanc DicomModalities).

Don't want to add the node to Configured nodes just to try it once? Switch to Enter details manually and type its AE Title, host, and port — the run uses them directly and nothing is saved.

C-STORE

Open

Sends one tiny Secondary Capture Image Storage instance. This tests whether the peer is a Storage SCP for that SOP Class — not whether your real modality’s SOP Class (CT, MR, US, …) will be accepted. Many archives accept Secondary Capture; some modality-only gateways do not.

The instance is identifiable on the PACS: patient ARNPRO^TESTBENCH, ID ARNPRO-TEST, modality OT. Do not send it to a production archive unless that is intentional. If C-ECHO works and C-STORE fails, the peer is not a Storage SCP for Secondary Capture (or that SOP Class is disabled).

PDF to DICOM

Open

Import PDF bytes, wrap each file as Encapsulated PDF Storage (SOP Class 1.2.840.10008.5.1.4.1.1.104.1), then optionally C-STORE the instances to a selected PACS. This is not the Testbench Secondary Capture image, and it does not rasterize PDF pages into pixel data. The Stored as (Modality) field in step 3 sets the object's Modality tag: DOC (the DICOM code for documents, and the default), SR or OT, or another code of up to 16 capital letters, digits, spaces or underscores. It is still an Encapsulated PDF; only the tag changes, for PACS that file or list documents by modality.

The page runs in four steps: choose the PDFs, the patient, the study and document, and where to send them. Step 1 takes PDFs from one source at a time. Choose it under Take PDFs from:

  • Files — one or more .pdf uploads only. Other types are rejected.
  • ZIP — only .pdf entries are used. Path traversal (..), __MACOSX, encrypted entries, and non-PDF files are skipped. Caps: 25 MB per PDF, 40 files, 40 MB ZIP, 80 MB uncompressed.
  • Folder — the browser’s directory picker. Only .pdf files are kept.
  • Directory on this workstation — a path this server can read. … opens a native folder dialog on this workstation (needs a desktop session; the Windows and macOS services have none, so the button is greyed out and you type the path). Scan lists PDF files only; other types are ignored. Hidden files and the filesystem root are skipped / refused. An operator can only pick a folder an administrator lists under Configuration > Security.
  • Patient Name / Patient ID — required (marked *) unless you generate them. Checking Generate fills the field with a value such as ARNPRO^PDFxxxx / PDFxxxxxxxx.
  • Accession Number, Study Description, Document Title — a value you type goes on every PDF in the batch as it is. Tick Generate next to a field to have it made for you instead: a new Accession Number per study (ACC plus ten characters), a Study Description per study (each file's name when every PDF is its own study, or PDF import and the date when Keep all PDFs in one study is on), and a Document Title per PDF (its file name). Document Title generates by default.
  • Generate, next to each field's label, fills one shared identity for the batch (useful when you do not have a real patient). One patient per PDF, named after its file derives Name and ID from each file name so a folder of reports does not land as one person on the PACS.
  • Keep all PDFs in one study — on by default. All PDFs in the batch share one Study Instance UID and Series Instance UID.
  • Store on a PACS — C-STORE Encapsulated PDF Storage to the Remote node, presenting as the chosen identity; both fields show only while this is checked. Uncheck to encapsulate only and see the SOP UIDs; the button then says Encapsulate instead of Encapsulate & send. The peer must accept that SOP Class; a green C-ECHO or Secondary Capture C-STORE is not enough.

Look the study up on the PACS with the Patient ID you typed. If association opens but Encapsulated PDF is rejected, enable that SOP Class on the archive (Orthanc usually accepts it with Storage).

Study Root C-FIND

Open

Query/Retrieve Study Root FIND — search stored studies in a PACS archive. This is not Modality Worklist. Leave filters empty for a broad STUDY-level query. Optional filters: patient name, patient ID, accession, study date, modality in study.

Zero matches with a Pass still means the SOP Class was accepted and the query succeeded. If C-ECHO works and Study Root C-FIND fails, the peer is not a Q/R SCP (or that information model is not offered). Use Worklist / MWL C-FIND for scheduled procedures. For Series or Image keys, or Vue Tamar tags, open Dicomtag Analytics from the sidebar (/tools/c-find-advanced).

Dicomtag Analytics

Dicomtag Analytics is its own product in the tool switcher (/tools/c-find-advanced). It shares this workstation's calling AE and remote nodes.

The query is one flat table with three columns: Return (a checkbox: send this key back as a result column), Field and Match value (a typed value is also a matching key). The usual rows are Study Date, Accession Number and Modalities in Study. Level (Study, Series, Image) and Report text are plain rows. Shortcuts is one menu: usual columns, all columns, SR series, or clear the filter values. Every other key (the rest of Patient, Study, Series and Image, plus the Vue/ELSCINT1 tags) is behind a closed More filters line with a count. Opening a saved query that used one of those other keys opens it automatically, so a saved search never hides a filter it depends on.

Wildcards. Text values take * (any characters) and ? (one character): *123* finds every Patient ID that contains 123. A % works like *, as in Vue's own search boxes, so %123% does the same; it is sent to the PACS as *123*. Dates, times and UIDs are not wildcarded. The same applies on the Find studies step of the Anonymizer and Cleaner and in Router rules. A Patient ID that really contains a % can therefore not be searched for literally.

Add other DICOM tags (under More filters) reaches every other attribute in the standard DICOM dictionary. Type a name, keyword or tag number such as patient weight or 0010,1030, tick one or more of the matches (ticks are kept while you search again) and press Add selected. Each added tag becomes a row you can return as a column, match on a value, or both, at the query level you chose; Remove takes it off again. Sequences and binary data cannot be used as keys and are not offered; tags already on the form are marked. Add a private (vendor) tag takes a tag with an odd group number, the private creator string and the value type (VR), for example (07a1,102a), ELSCINT1, CS. Added tags are saved with the query and used by Dicom Router rules loaded from it. A PACS ignores, or may reject, a tag it does not support, so check the results, and type a value the way its type expects: dates as YYYYMMDD, age as 030Y, codes in capitals.

Study Root FIND at Study, Series, or Image, including optional Tamar / ELSCINT1 keys. Hierarchical FIND: Series needs Study Instance UID; Image needs Study and Series Instance UID. Tamar Assign To Doctor (07a1,1042) is a confirmed matching key on Vue 12.2.8 (used with Modalities in Study, for example CT). Study Date is required at Study level — use the period menu (Any date, Today, Yesterday, Last 7 days, Last 30 days, This month, or Date range…; a range shows two date boxes) instead of typing YYYYMMDD by hand; the text box beside it still shows the exact value being sent and still accepts manual DICOM date syntax (a single day, or an open-ended range like -20260101). Modalities in Study is a dropdown checklist of the common codes (CR, CT, DX, MG, MR, NM, OT, PT, RF, SC, SR, US, XA) that shows what is ticked ("CT, MR" or "Any") — tick several (for example CR and DX) to match any of them; typing an uncommon code directly into the value box still works and is kept alongside whatever is ticked. After a Study query, List SR reports runs Series C-FIND with modality SR for every study in the table. List series is the same per-study drill-down for any Series Description — type a value (e.g. POSITIVE, from an AI tool that writes its result there) or leave it blank for every series; Series Description, like any Series key, needs a Study Instance UID in the hierarchical model, so this is how it searches across many studies without one typed in by hand. Both run one Series-level C-FIND per study in the table, so narrow the Study-level filters first on a large result. Checking Also search series (under Level, Study only) does both passes in one submission instead of two: the Study query runs, then every matched study is drilled into Series automatically, and the combined series table is what comes back — equivalent to running the Study query and then clicking List series yourself, just in one click. A Series Description there uses the same wildcard syntax as any other field: *POSITIVE* matches anywhere in the value, not just an exact match. A comma-separated list (POSITIVE, NEGATIVE, DOUBT) ORs several values together — DICOM has no OR for one matching key, so that is one C-FIND per study per value, merged into one table. A series-level result (from either path) still carries each row's Study Instance UID, so List SR reports and List series stay available to chain further from there. Retrieve report text C-MOVEs each listed report on its own association onto this AE (when Accept C-STORE is on) and parses the DICOM Content Sequence — no language model, and no C-GET. JSON/CSV export includes Findings and Impression as columns plus the full report text. The Query page is a compact key tree on the left and the result table on the right.

Saved queries. After a study, series or image query returns, Save this query under the results keeps it under a name: the remote node, Present as identity, level, checked columns, filter values and report-text options. Saved queries are listed in the product's sidebar; opening one fills the form in, and you press Run query yourself. A Study Date set with a preset (Today, Yesterday, Last 7 days, Last 30 days, This month) stays relative, so "Last 7 days" means the last seven days whenever you open it; a date you typed or picked stays fixed. Saving under a name that already exists replaces that query, and Delete on an opened query removes it. Follow-up runs (List SR reports, Retrieve report text) aren't saved; save the query they started from. Saved queries are kept in saved_queries.json in the data folder.

There is no separate Patient-level query — Patient Name, Modality, Study Date, and Tamar Practice Settings Code (07a3,105c) (the radiology department) are all already Study-level keys, so filter on those at Study level and use them together in one query. A Study result table that includes Patient Name shows a Count patients by name button: it groups the rows by the first letter of the patient's family name (for example "A: 500, B: 1300, ...", with # for anything that isn't a letter), counting each distinct patient once — deduplicated by Patient ID, or by Patient Name when Patient ID is blank — not once per study, so a patient with several studies in range is not over-counted. It shows an approximate count immediately from the table already on screen. If that table was capped at 2000 studies, it automatically re-runs the same query in the background — asking only for Patient Name and Patient ID, with the cap raised to 50000 — and swaps in the exact count once that returns; nothing to click, nothing to narrow by hand. Only past 50000 matching studies does it give up and ask you to narrow Study Date (or another filter) yourself.

Open

Send Image to PACS

Open

Attaches a placeholder image to a study. 1. Find a study offers three ways, chosen on the Find the study by row (its ? explains when to use which): Study runs the same Study Root C-FIND as C-FIND / Dicomtag Analytics, which finds a study whether its order is still open or already closed — Modality Worklist, by contrast, stops listing an order the moment it's performed. Patient is Patient Root C-FIND at Patient level, for an order whose study has no image yet stored at all — Study Root C-FIND can't find that either, since it only matches studies with at least one stored instance, but many PACS keep a patient record (registration/demographics) independently of any study. Details typed by hand is the last resort: skips any lookup and takes the typed-in Patient Name and Patient ID as-is, for when even the patient isn't registered. All three leave Accession Number and Study Instance UID for step 3, except Study Root C-FIND's own values, which step 3 can still override. 2. Pick the study — exactly one; this sends a single image, not a batch. 3. Describe the image — choose the Modality the stored object is tagged as, set or override the Accession Number and Study Instance UID (left blank, a new UID is generated), plus optional Study Description, Body Part Examined, and Series Description. 4. Send picks a destination, defaulting to the same node selected in step 1.

The image itself is a fixed small solid-black frame (Secondary Capture Image Storage) — there is no real pixel content to configure. What makes it identifiable is the Patient Name, Patient ID, Accession Number, and Study Instance UID from the picked study and step 3, so the stored instance lands in the same study it refers to.

HL7 send

Open

Sends an HL7 v2 message to a TCP endpoint. It is a sender, not an analyzer: paste (or save) the pipe-delimited text and ship it. The editor shows one segment per row (toggle Raw for the full paste). Long lines wrap. Newlines become CR on the wire.

  • Host / port — the HL7 listener, not the DICOM port. Typical engine ports are 2575 or 6661, not 104 / 4242.
  • Framing — MLLP (0x0B … 0x1C 0x0D) is the default. Raw TCP is there for engines that do not wrap.
  • ACK — if the peer replies, the result shows the raw ACK, MSA-1 (AA / AE / AR), and ACK MSH-3 (who answered). An ACK is not a promise that PACS applied an order update.
  • Saved drafts live in hl7_messages.json next to config.

The page runs in four steps: Destination (a remote node's host or a typed one, port and framing, with a folded note for Philips IS Link), Message (the editor, and Save as / Save message), Adjust before sending and Send. Saving a message keeps the host, port and framing on the page.

Adjust before sending

Folded by default; its heading lists the rewrites that are on (for example "New MSH-10 · ORC-1 → SC"), so you can see what will change without opening it. Each option has a ? with a one-line summary and a folded Details note. They only rewrite fields the message already has and never invent missing ORC / OBR segments. All four are off by default: each one changes the message, so turn on only what you mean to test. The IS Link details here come from Philips' Vue PACS 12.2.8 HL7 Interface Specifications (HA1669) and the HL7 code tables; they have not yet been checked against a live IS Link server.

  • New Message Control ID (MSH-10) — a new Message Control ID so a resend is not treated as a duplicate. The same MSH-10 is often ACKed and ignored.
  • Change existing order (ORC-1) — overwrites ORC-1 with the chosen order control and stamps ORC-9. It does not invent an ORC. Repeating NW is usually ACKed and skipped.
  • ORC-1 order control — the IS Link specification for Vue 12.2.8 defines only NW (add), SC (update) and CA (cancel). In standard HL7 (table 0119) SC means “status changed” and XO is the change request; Vue often ignores XO while Mirth still ACKs. XX (changed, unsolicited) is also offered. This is not OBR-25 SC. IS Link replaces the whole segment on an update: a field that had a value and is empty in a later message is deleted, so send the complete ORC and OBR.
  • Reason for Study (OBR-31) — sets OBR-31 to code^text from the Code and Text fields (a missing code is the text's first word). With both empty, it keeps the existing reason and only makes it a proper id^text CE. The IS Link specification lists DICOM (0040,2010) for OBR-31, but in DICOM that tag is Order Callback Phone Number, so that looks like an error in the document; the reason usually lands in (0040,1002) Reason for the Requested Procedure or (0032,1030) Reason for Study. Which one Vue fills is not confirmed. It may not be the study description you see in the Vue UI (that is often OBR-4.2 / C-STORE).
  • Set exam status (OBR-25 and ORC-5) — test only. Choose the OBR-25 result status and the ORC-5 order status. OBR-25 uses HL7 table 0123 (single letters: O I S A P R F C M N X, such as P preliminary, F final); Vue maps it to DICOM Interpretation Status ID (4008,0212), the same as OBX-11. The default SC is not in table 0123 (it is an order status); it is kept as the earlier Vue test. ORC-5 uses table 0038; IS Link documents only SC (scheduled) and CA (cancelled), and it is left as it is unless you choose one. OBR-25 is result status, not Vue’s ORC-1 SC. An ACK does not rewrite stored images.

The Send result repeats MSH-10, MSH-5 / MSH-6, ORC-1, OBR-25, and OBR-31 as they went on the wire, plus a Hint when the ACK is likely not a PACS update.

Philips Vue PACS + IS Link

The ACK you see is from whoever answers on Host/Port. On Vue, IS Link Configuration → Listeners shows Port Number (often 10010) and Host IP. That Listeners page is settings, not the inbound queue. Control Port (often 2112) is not MLLP. Encoding Cp1252 matches Latin-1 for ASCII HL7.

  1. Send to the Listener Host IP:Port Number. After Add/Edit Listener, IS Link reminds you to start the Listener process.
  2. Look at Queues & Notifications, not the Listeners form. A message there means routing worked; then ORC-1 SC, accession, and OBR-31 can matter.
  3. Still empty with connection refused / timeout: wrong Host IP, Listener down, or this workstation cannot reach that VLAN.
  4. Still empty but you got an ACK: ACK MSH-3 is who answered. If it is Mirth/IBE, Host is not this IS Link. MSH-5 / MSH-6 must match what IS Link accepts.
  5. Vue order control is NW (new), SC (update), CA (cancel). XO is not in that table. Match the accession Vue already has: ORC-3 / OBR-3 and often OBR-18.
  6. Updating an existing study may also need Vue’s ZDS Study Instance UID. HL7-PACS Field Mapping in that same tree decides which ORM fields actually overwrite.

Tag Editor

Open

Corrects two private ELSCINT1 tags CS PACS REPORT writes onto every instance in a study — Tamar Report Final Sign Timestamp (07a3,10fb) and Tamar Report Study Last Composed By (07a5,1040) — when a report workflow gets stuck, then C-STOREs the correction back to the PACS.

The page runs in four steps: Connect (remote node and Present as), Find the study, Check current values (Fetch) and Push new values. Seed test studies is folded away under Practise on test studies at the bottom.

  • Seed test studies C-STOREs two throwaway studies (patient ARNPRO^TESTBENCH) — one with both tags present but blank, one with them entirely absent — so Push can be tested against the actual missing-data case without touching a real patient. Needs no Accept C-STORE, same as the C-STORE test tool.
  • Find Study Instance UID resolves it from Accession Number and Study Date (both required) with a plain Study-level C-FIND — no Accept C-STORE needed for this step. Exactly one match fills in Study Instance UID below; more than one lists them so you can pick the right one.
  • Fetch C-MOVEs the study (or one series, if you give a Series Instance UID) to this AE and shows the current value of both tags per instance, same as Dicomtag Analytics report retrieve — Accept C-STORE must be on and this AE must be a C-MOVE destination Vue knows about.
  • Push retrieves fresh, overwrites only the field(s) you filled in, and C-STOREs every retrieved instance back — Vue mirrors both tags onto every instance in a study, so a partial fix would leave the study inconsistent.
  • Only overwrites a tag that is already present. An instance that never had one of these tags is left alone for that tag and noted as skipped — this tool never invents a compose/sign event. If the real stuck case turns out to have the tag entirely absent rather than present-and-blank, Push cannot fix it as built; that would need deliberately relaxing this safety rule.
  • Tested once against a real Vue archive, on an already-complete study: C-MOVE and C-STORE both reported success, but the stored object was not actually replaced — a Fetch right after a Push still showed the old values. That only shows Vue ignores a C-STORE that changes an already-filled field; it says nothing about the actual target case (a genuinely missing value), which Seed test studies exists to let you check. Two things worth ruling out first regardless: whether Vue's report UI has a "re-open / re-sign" action for a stuck report (would go through the same internal path that sets these fields correctly on every normal report), and whether this is a one-off vendor-side bug worth a Philips/Vue support escalation. A separate distribution log shows these fields are required input to Vue's own report-distribution step, not something an inbound HL7 message could supply — so fixing this via HL7 sent to Vue is not a workable direction.

Dicom Anonymizer

Dicom Anonymizer is its own product in the tool switcher (/tools/anonymize). It shares this workstation's calling AE and remote nodes. It has four numbered steps: find studies, choose studies (and series), choose how, export.

  • Find studies is a Study-level C-FIND on Patient ID, Accession Number, Study Date (required), and Modality — the same fields, wildcards (*123*, or %123%) and rules as Dicomtag Analytics. Modalities is one dropdown checklist. The result is a checkbox table; check the studies you want to anonymize.
  • Anonymize at chooses the granularity. Study retrieves and anonymizes exactly the checked studies. Series or Image first walks down from each checked study (an internal C-FIND to every series, and for Image every image in every series) and anonymizes all of them.
  • Show series, under each study row, picks series yourself. It lists that study's series (number, modality, description, number of images), all ticked; untick what to leave out, and only the ticked series are retrieved and anonymized, one C-MOVE per series. A study whose series you never opened is handled by the level above. For an opened study the ticked series win over the level.
  • Nuke all information rebuilds each instance from only the tags a DICOM viewer needs to open it — Rows, Columns, pixel data, Modality, and fresh Study/Series/SOP Instance UIDs — and drops every other tag entirely, including ones this page doesn't otherwise know about.
  • Fuzz all data keeps every tag present but replaces its value with scrambled placeholder data (dates become 1900-01-01, names and free text become random letters, numbers become 0). Pixel data and the same handful of image-structure tags as Nuke are left alone so the image still decodes; UIDs are remapped, not fuzzed as text.
  • Remove patient information only touches a curated list of roughly 50 patient-identifying tags (patient name/ID/birth date/sex/address/phone, referring and performing physicians, operator, institution and station name, and a few more — not the full DICOM standard list) — erased blank or scrambled, your choice. Everything else on the instance (Study Description, Series Description, equipment fields not on that list, and so on) is left untouched.
  • Custom shows that same tag list, grouped by category, with a per-tag choice: keep as is, erase, or replace with a value you type. UID tags (Study/Series/SOP Instance UID, Frame of Reference UID) can only be kept or given a fresh UID — a UID cannot be blanked or given arbitrary text and still be a valid DICOM identifier.
  • Every mode routes Study/Series/SOP Instance UIDs it changes through one shared map for the whole run, so instances that shared a UID before anonymizing (the same study, the same series) still share one afterward instead of each becoming its own orphan study.
  • Output folder is a folder on the computer the app runs on, and the app's own account must be allowed to write there. Type the path: the Browse… button opens a folder dialog on that computer, so the Windows and macOS services (no desktop) grey it out, and operators may only use folders an administrator lists under Configuration > Security. Archive is no archive (loose files in a new timestamped subfolder) or a ZIP. 7z archiving is not implemented yet.
  • Folder layout: Subfolder per series (the default: a folder per study, a folder per series inside it) or All files in one folder. With subfolders you can choose the study folder name (the Study UID, or the study description) and the series folder name (number and modality such as series-3-CT, or the series description such as TLC Inspiratory 0,6). A description is taken from the original and is not anonymized, so it can contain identifying text; that is why the default is the UID or the number. Characters Windows does not allow in a folder name become _, names are cut at 80 characters, a series with no description is named by number and modality, and two with the same name get the series number or the end of the UID added. File names are always built from the anonymized UIDs, never the originals.
  • The result lists every selection with how many images came back, then a table with one row per anonymized study (series and instance count). Some PACS close the association after a few C-MOVEs; a selection that gets nothing for that reason is retried once on a new association. If a selection still returns nothing (it is named with the reason, for example 601 · TLC Inspiratory 0,5 (C-MOVE status 0xC000)) or some instances could not be anonymized, the run is a Fail that says what was exported and what was not, not a plain success.
  • Retrieve needs Accept C-STORE on and this AE listed as a C-MOVE destination, same as Dicomtag Analytics and Tag Editor retrieve.

Dicom Router

Dicom Router is its own product in the tool switcher, since it is a background service you manage alongside everything else rather than a one-off query.

  • The Route rules page lists every rule with its state, schedule, source and destinations, last run (OK or Failed) and next run, with Start / Resume, Run now, Pause, Stop and Edit on each row. Add route rule opens the form; when there are no rules yet, the form is shown straight away. The form's main fields are Name, Source PACS, Modality, Query level, Study date and Number of days; Schedule, Forwarding and Export matches to a file are folded sections. The Status dashboard button opens the status dashboard.
  • The product's left sidebar lists the same rules on every page under it, each with its state in words (Active, Paused, Stopped, Running) and a matching dot. Click a rule in either place to open its own page with the run history.

A PDF rule (Kind: Watch a folder for PDFs) does not query a PACS. On each run it looks at the top of one folder, wraps every new PDF as Encapsulated PDF Storage and sends it to the node in Send to. A File name pattern such as {PatientID}_{PatientName}_{Accession} reads those values from each file's name (tokens: {PatientID}, {PatientName}, {Accession}, {Description}, {Title}, {*} to ignore a part; put a separator such as _ between them); a file whose name does not fit moves to Failed. Without a pattern, Patient is named after each PDF's file, one typed patient, or generated; Accession Number, Study Description and Document Title can be typed or generated, as in PDF to DICOM. A sent file moves to a Sent subfolder, a file that is not a PDF moves to Failed, and a PDF the PACS refused stays and is tried again at the next run. Subfolders and hidden files are ignored, and a file changed in the last 10 seconds waits. The folder must be readable and writable by the app's account (the service account in the Windows and macOS services). The dashboard shows Sent and Failed PDF counts; file names and patient data are not stored.

A route rule (query kind) is a scheduled Study Root C-FIND (an interval in minutes, or specific times of day with optional days-of-week) against a configured remote node, filtered by modality, study date scope, and query level (Study, or Series per matching study). The scheduler runs due rules automatically and records what is new since the rule last ran, using the same de-duplication idea as Dicomtag Analytics' SR retrieve — nothing already handled is reported again.

Adding a rule can start from a saved Dicomtag Analytics query (Study level only, the "Load saved query" row at the top of the form): it copies the query's remote node, Modality, and any other filter it had — a one-time copy, not a live link. Study Date is not copied; the rule's own "Study date" control re-derives that on every scheduled run instead of replaying a one-off snapshot.

  • A rule with no destination nodes only tracks new studies (find-only) — nothing is retrieved or moved.
  • Add one or more destination nodes and the scheduler additionally C-MOVEs each new match to this workstation's local Storage SCP — same Accept C-STORE setting Dicomtag Analytics' SR retrieve and Tag Editor Fetch use — and C-STOREs it on to every destination, using the retrieved object's own SOP Class. There is nothing to pre-register per rule.
  • A study is only marked "seen" once it is fully handled (found-only for a find-only rule, forwarded to every destination for one that has them), so a failed retrieve or forward is retried automatically on the next run instead of silently dropped.
  • Set an Export folder and each run also writes (or overwrites) <rule-name>-YYYY-MM-DD.json there — that run's matches as Study Instance UID, Study Date, Accession Number, Modality, Study Description and status, deliberately without Patient Name or Patient ID. This is independent of destination nodes: a find-only rule can export too. It is a plain data drop for a separate reporting/graphing tool to read, not something this app displays — a daily rule with Study Date set to "Today" gives that tool one file per day.

Each rule can be Started, Paused, or Stopped independently of its own schedule — from the route rules list, or on the rule's own page:

  • Start runs the rule immediately and computes a fresh next scheduled time, whether it was paused or stopped before.
  • Pause and Stop both stop the schedule from firing again, and both interrupt a run already in progress — cooperatively, between studies rather than mid-association, so nothing already retrieved or forwarded is ever redone or lost. They differ only in what is left behind: Pause keeps the rule's previously computed next-run time as a record; Stop clears it.
  • Run now executes a rule immediately without touching its status or schedule — useful for testing a paused or stopped rule.

Manual runs (Run now, and the run Start triggers) execute in a background thread instead of blocking the browser request, which is what makes Pause/Stop clickable while a batch is still going and lets the sidebar show a live "Running" dot. Each rule's own page shows a run history with every match and its status (found / retrieved / forwarded / failed, with the error if any) and whether the run itself completed or was interrupted.

Dicom Cleaner

Dicom Cleaner is its own product in the tool switcher (/tools/dicom-cleaner). It shares this workstation's calling AE and remote nodes.

  • Find studies is a Study-level C-FIND on Patient ID, Accession Number, Study Date (required), and Modality — the same fields, wildcards and rules as Dicomtag Analytics and Dicom Anonymizer. The result is a checkbox table; check the studies you want to clean.
  • Level chooses the granularity, same as Dicom Anonymizer: Study, Series, or Image.
  • Redact region is one rectangle — X, Y, Width, Height in pixels, top-left origin — blacked out to zero on every retrieved instance's pixel data. Width or Height of 0 means "to the edge" in that direction. It uses each dataset's own tags (number of frames, samples per pixel) to redact the right axes, so single-frame color and multi-frame grayscale images are never confused. Compressed Transfer Syntaxes need pylibjpeg or gdcm installed to decode, same as any other pydicom pixel read. Burned-In Annotation (0028,0301) is set to NO on every cleaned instance. The same rectangle is applied to every retrieved instance, so setting it once covers every image in the checked study/series. An optional Label burns a short text stamp (e.g. "REDACTED") into the same black box, in white at the pixel data's own brightest value — dropped automatically if the box is too small to fit even one character.
  • Pick the region on an image retrieves one image from the first checked study and draws a rectangle on it visually instead of typing coordinates blind — Browse images in first checked study lists the study's images, Load image retrieves the picked one and renders it (a plain min-max stretch, not a diagnostic display), then dragging on it fills in the Redact region fields above.
  • Dicom Cleaner only touches pixel data and Burned-In Annotation — it does not scrub PatientName, PatientID, or any other tag the way Dicom Anonymizer's modes do. Run both tools on a study that needs both kinds of cleanup.
  • Send back as chooses the SOP Instance UID strategy for the C-STORE back to PACS: New UID (default) sends the cleaned image as a new object, leaving the original untouched on the PACS; Same UID reuses the original SOP Instance UID, which only replaces the stored instance if the destination PACS actually overwrites on a duplicate — check that behavior before relying on it.
  • Assign a new Series Instance UID groups the cleaned images into a brand-new series instead of merging back into the original one — every image retrieved from the same source series shares one new Series UID, not one each. Checking this always assigns a fresh SOP Instance UID too, regardless of the "Send back as" choice above, since keeping the original SOP Instance UID while moving it to a different series would be ambiguous.
  • Send to defaults to the same node the study was retrieved from; pick a different configured remote node to send the cleaned instances somewhere else instead.
  • Retrieve needs Accept C-STORE on and this AE listed as a C-MOVE destination, same as Dicomtag Analytics and Dicom Anonymizer retrieve.
  • The cleaned images are written back to a PACS, so a gap matters. If the PACS closes the association part-way, a selection that got nothing is retried once on a new association, and the result lists every series (or image) with how many images came back. If anything is missing, or an image could not be redacted, the run is a Fail that says how many instances were sent and what was not.

Dicom Import

Open

Brings DICOM files from a folder into a PACS: a CD or DVD export, a USB stick, or a folder of files. It has four steps. 1. Choose the folder: type a path on the computer this app runs on, or press … to browse (the browse button needs a desktop session; the Windows and macOS services have none, so it is greyed out and you type the path). The folder can hold a DICOMDIR, loose DICOM files, or both, in any depth of sub-folders; the files are only read, never changed. 2. What was found sums up the folder from the DICOM tags: how many patients, studies, series and images, the size, and a table per study with its date, description, accession number, modality, series and image count. Warnings say what to check: files that are not DICOM (ignored), files missing a UID (left out), a repeated SOP Instance UID (only the first is kept), one patient ID with two different names or birth dates, files the DICOMDIR lists but are not on disk, files in the folder that the DICOMDIR does not list (still included), and compressed images.

3. Review and change details is optional. Every patient and study has its details in editable fields: patient name, ID, birth date and sex; study description, accession number, date, time, referring physician and study ID. Only fields you change are written, and only while the images are sent, so the files on disk are never modified and no edited copy is made. Send to the PACS stores the chosen studies over C-STORE to a remote node, as the calling AE you choose. Progress shows while it runs; Stop ends it after the current file, and the result lists any file that failed with the reason. Change and send again returns to the review.

Two options. Give the studies, series and images new UIDs is for when the PACS may already hold these studies and they must not merge with or overwrite them; links between images, such as a report pointing at its images, follow the new UIDs. Leave it off to import them as they are. Decompress an image the PACS does not accept in its own format is on by default: a compressed image goes as it is when the PACS accepts its format, and is otherwise decompressed (which needs a decoder for that format; a failure is reported for that file).

Nothing about the patients is stored. The scan lives in memory only and is dropped when you start over or after 30 minutes idle. Under the Windows headless edition the service reads the folder as its own account (LocalService), so the folder must be readable by it, and a mapped drive letter such as Z: is not visible to a service: use a local path or a network path that account may read.

Status dashboard

Open

A simple page for a screen on the wall (/lite), opened with the Status dashboard button on the Dicom Router page. A viewer account lands here after signing in. It shows one tile per Dicom Router rule, refreshed every few seconds, built from the rule's newest run, so it needs no export folder.

  • A small coloured square before the rule's name says the state: green (the last check worked), red (it failed, with the reason), grey (no recent check, or waiting for the first one). A rule that has not checked for much longer than its schedule is shown as having no recent data.
  • The tile shows how many exams the last check found, per status when the rule has a Status check key (for example TamarStudyStatus), with the modalities for each status. Without a key it shows one matched count.
  • Under the counts is a history chart: exams per day for the last 7, 14 or 30 days (the buttons in the header; your choice is remembered in this browser). A rule with a status key gets one chart per status value, so a rule that counts PENDING FINAL shows that status on its own. The day is the exam's study date, so a rule that looks back several days works too. A dashed mark means the rule had no successful check for that day, which is not the same as zero. Hover a bar for the exact number.

The charts come from counts the Router keeps for each study date (route_daily.json): counts only, no patient data, deleted after 30 days by default like the run history (Configuration > Security). Days from before this was added cannot be rebuilt: a rule that looks back several days fills its chart at its first check, and a "today" rule builds one bar per day from then on.

Reading accepted vs rejected SOP Classes

After a DIMSE association, the result lists presentation contexts the peer accepted and those it rejected. Read that list before you trust a green/red summary:

  • Accepted Verification / Secondary Capture, rejected Encapsulated PDF — C-STORE test image works; PDF to DICOM will not. Enable Encapsulated PDF Storage on the archive.
  • Accepted Verification / Storage / Study Root, rejected MWL — stock Orthanc without the worklist plugin. Query the archive with Study Root C-FIND; query a RIS (or enable the plugin) for MWL.
  • All requested SOP Classes rejected, or association aborted — called AE, host, or port wrong; or the calling AE is not allowed.
  • Pass with zero rows — the FIND SOP Class was accepted and the query succeeded. Empty is a filter / data problem, not a connectivity failure.

Import / export of settings

Open

Under Configuration → Import / export. It moves your settings to another computer, or into the Windows headless edition (which starts with its own empty data folder), in one JSON file. Export downloads the parts you tick: remote nodes, virtual AEs, local AE settings, saved Analytics queries and Dicom Router rules. Results, the worklist, router run history, HL7 drafts and logs are never included, because they can contain patient data. The file lists PACS hosts, ports and AE titles but no passwords, so treat it as internal. Local AE settings belong to one computer, so they are off by default; saved queries are off by default because a query may hold a patient ID or name typed as a filter. Router rules are exported without their run history.

Import is two steps. Choose the file and press Check the file: you see what would be added, updated or left as it is, with warnings, and nothing is written yet. Then Import the ticked parts applies it in one go, and puts everything back if anything fails halfway. Import only adds and updates; it never deletes. A record matches one you already have by id, then by name, so importing the same file twice changes nothing. Links between records (a rule pointing at its PACS, a saved query pointing at a node or virtual AE) are rewritten to the ids used on this computer; a link to a node that is not here is a warning. New router rules come in stopped, so nothing queries a PACS the moment you import; a rule you already have keeps its running state, as when you edit it. A rule's export folder is machine specific, so check it exists on the new computer. The uploaded file is held in memory between the two steps, never written to disk, and dropped after use or after about twenty minutes.

A legacy ./data folder is used only if it already has config.json and the home folder does not.

JSON API

The same operations as the UI are available over HTTP. GET /health returns {"status":"ok","version":"{{ app_version }}"}. There are no interactive API docs in a shipped build (/docs is switched off); the endpoints are listed in the README.

Tool ids: ping, c-echo, c-store, pdf-store, c-find, c-find-advanced, mwl-find, hl7-send, tag-editor. hl7-send does not need a remote id; pass host, port, and message in options. pdf-store takes Patient Name / ID in options, plus pdfs (filename + content_b64), zip_b64, or directory, and send (default true). c-find-advanced takes level (STUDY, SERIES, IMAGE), values (DICOM keywords), and optional return_keys. At Study level, Study Date is required. Follow-ups: follow=sr_series with studies (Study rows) lists SR series; follow=retrieve_sr C-MOVEs each listed report on its own association. tag-editor takes action (seed_test, lookup, fetch, or push). seed_test takes no other options and needs no Accept C-STORE. lookup takes accession_number and study_date (both required) and returns matching studies. fetch / push take study_uid, optional series_uid, and for push at least one of final_sign_timestamp (YYYY-MM-DDTHH:MM:SS) or last_composed_by. DIMSE tools take remote_id and optional identity_id for a virtual calling AE. Worklist query source is local or a remote id. The Anonymizer, Cleaner, Import and Send Image (anonymize, dicom-cleaner, dicom-import, send-image) are built around their pages; use the UI for those. The status dashboard has GET /lite/api/status and GET /lite/api/history?days=7 (7, 14 or 30), both open to viewers.

The API follows the same sign-in and roles as the UI. With no account on one computer it opens without a login; once sign-in is on, a request without a signed-in session gets 401 (there are no API keys, only the session cookie from signing in), and an account may only call what its role allows. Restrict it the same way you restrict the UI.

Talking to Orthanc

Typical Orthanc DICOM port is 4242. From Docker on a Mac, host is host.docker.internal.

  1. Add a remote: AE Title ORTHANC (or whatever Orthanc uses), host host.docker.internal or the LAN IP, port 4242.
  2. In Orthanc DicomModalities, allow this tool’s calling AEs — the workstation (DICOMM by default) and every virtual title you will impersonate (CT1, …).
  3. Testbench: C-ECHO should pass if the association is accepted.
  4. C-STORE / Study Root C-FIND usually pass on a stock Orthanc Storage / Q/R setup.
  5. MWL C-FIND passes only if the Orthanc worklist plugin (or equivalent) is enabled and that SOP Class is offered. Otherwise the Testbench shows MWL rejected. That is expected.

Troubleshooting

Symptom Likely cause
Association rejected / aborted Called AE, host, or port wrong; calling AE not in the peer’s allow-list
C-ECHO works, C-STORE fails Peer is not a Storage SCP for Secondary Capture (or that SOP Class is disabled)
C-ECHO / C-STORE work, PDF to DICOM fails Peer does not accept Encapsulated PDF Storage. Enable that SOP Class; Secondary Capture is a different test.
C-ECHO works, Study Root C-FIND fails Peer is not a Q/R SCP. This is not MWL.
Dicomtag Analytics Series/Image stays locked or fails Hierarchical FIND. Fill Study Instance UID for Series; Study and Series Instance UID for Image. Empty Study UID cannot search body part archive-wide.
List SR reports returns zero series Those studies have no series with modality SR, or Vue omitted Modality. Confirm an SR series exists in the study.
Retrieve report text returns one report from a long list Vue accepted one C-MOVE per association. Retrieve opens a new association per report. The buttons show the row count; the summary is Retrieved N of M. A clicked row does not limit retrieve to that exam.
Retrieve report text: Move Destination unknown Vue does not have this workstation AE as a C-MOVE destination. Register the Local AE Title at this host:port. Enable Accept C-STORE on Local DICOM AE.
Anonymizer or Cleaner: some series are missing and the run says Fail The PACS closed the association or refused those series. The C-MOVE step lists every series with how many images came back and the reason (for example C-MOVE status 0xC000, or no response). A dropped association is retried once on its own; if a series still comes back empty, check the PACS log, and that this Local AE is registered as a C-MOVE destination.
The … / Browse button is greyed out (Anonymizer, Import, PDF to DICOM) The app runs as a background service (Windows or macOS) with no desktop, so it cannot open a folder dialog. Type the path of a folder on the computer the app runs on. The service account must be able to read it (and, for the Anonymizer, write to the output folder).
Searching Patient ID with %123% or *123* finds nothing The query is sent to the PACS as *123*. Whether the PACS treats that as "contains" is up to the PACS; try 123* and *123, and check the PACS's own query rules.
C-ECHO / C-STORE / Q/R work, MWL fails Peer does not offer Modality Worklist FIND. Enable the worklist plugin (Orthanc) or query a RIS.
Worklist and MWL C-FIND look the same They are the same SOP Class. Use Testbench Study Root C-FIND to search stored studies.
Empty MWL / C-FIND table but Pass The SOP Class was accepted and the query succeeded with zero matches. Check station AE, date, and Present as.
HL7 send times out / no ACK Peer is not listening, or that port is DICOM not MLLP. HL7 engines are often 2575 or 6661, not 104 / 4242.
HL7 ACK AA to 10010 but Vue IS Link “empty” Listeners is settings, not the queue. Look at Queues & Notifications. Send to Listener Host IP:10010, not Control Port 2112. Confirm the Listener process is started. ACK MSH-3 is who answered.
HL7 ACK AA, IS Link queued, Vue UI unchanged Vue updates with ORC-1 SC, not XO. Accession must match ORC-3 / OBR-3 (and often OBR-18). OBR-31 goes to the reason for the study (the IS Link spec's (0040,2010) looks like a documentation error); the Vue UI may show Study Description from C-STORE instead.
PING ICMP fails, TCP succeeds Normal on locked-down clinical networks. Trust TCP to the DICOM port.
Cannot reach Orthanc from Docker Use host.docker.internal (same Mac / host) or the LAN IP; publish / check 4242.
Config vanished after image rebuild Config should be in ~/.dicommunication (the Windows service: C:\ProgramData\Dicommunication). Legacy ./data is only used until the home folder exists.
